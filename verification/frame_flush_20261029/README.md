# 帧清空信号毛刺修复：底部缺失与固定列错位

日期：2026-10-29。实板先出现底部黑区，诊断版仅FIFO欠载灯亮；读返回吞吐优化后底部可见，但出现固定的横向循环错位且普通LED4亮。用户在TD重新编译下载，当前源码/报告与上一轮修复配置一致，不能归因为用户下载了已知旧版本。

## 发现的具体缺陷

`read_RAM.v` 原实现用 `vcnt == 480` 组合译码生成 `frame_sync`。它通过 `display_pixel_fifo.v` 的 `fifo_reset_n = Reset_n && !blank_flush` 直接成为异步FIFO和输出队列的异步复位源。

二进制行计数多位翻转时，寄存器Q和组合路径延迟不同，译码可能短暂错误命中480。例如383→384：低五位较早归零、bit7升高而bit5/6稍后归零时，中间组合可为480。类似的多位翻转还可能出现在255→256。一次极短错误脉冲就可能清除部分或全部FIFO状态，而memory域两级同步后的清空信号可能根本看不到它，reader继续原来的数据序列，造成数据丢弃、列循环错位并最终欠载。

显示FIFO深度2048，2048 % 640 = 128；若接近满FIFO的预取数据丢失，可能留下接近128像素的列偏移和数行位移，与照片相符。但目前没有实板毛刺波形或丢字数量采样，不能把2048当作实际测得的丢字数。

上一轮将受控延迟下的欠载归结为吞吐余量，未检查组合译码用作异步复位的硬件毛刺风险，诊断不完整。普通零延迟RTL仿真把同一个计数器向量同时更新，因此看不到这种中间译码；时序裕量通过也不等同于组合异步复位信号无毛刺。

## 修改

仅修改 `rtl/display/src/read_RAM.v` 的frame生成：在像素时钟下，仅当hcnt=799时，根据旧vcnt是否为479更新寄存器frame。进入第480行时拉高，离开该行时拉低，复位时清零；输出仍覆盖完整第480行，消除二进制行计数器组合译码直接驱动异步复位的路径。

原有计数、VSYNC、像素请求、图像坐标与HDMI数据连接保持原逻辑。保留上一轮reader边收边送优化，PLL、SDC、ADC、FIFO深度和写控制器均未改。用户现有修改保留。
