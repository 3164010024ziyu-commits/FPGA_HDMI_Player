# 图片信息字幕与音频播放进度

2026-11-03，基于memory `a2ee12a`。用户确认普通字幕默认显示当前图片序号、文件名、尺寸，时间显示当前音频的播放进度。本版已实现并完成仿真、综合、布局布线和时序检查，尚未上板。

## 显示与控制

- 普通字幕示例：`图片 00001 TEST.BMP 640x480`。序号从1开始，跟随实际前台图片；没有图片时显示“暂无图片”。
- 图片字幕位于x=16..623、y=452..467；音频时间位于x=16..191、y=12..27，格式为`音频 00:02:35`。16×16像素单元，白字、右侧黑影、半亮度底条，与右下角频谱和右侧参数提示错开。
- 文件名使用Storage已有的FAT 8.3短文件名，去除主文件名尾部空格并补上扩展名分隔点；不是新增长文件名/任意Unicode文件名支持。不支持的非ASCII文件名字节显示方框。

| 控件 | 引脚 | 功能 |
|---|---|---|
| SW1 | C8 / key_in[4] | 向下显示音频进度，向上隐藏；隐藏不影响播放和计数 |
| SW2 | C7 / key_in[3] | 向下显示图片信息，向上隐藏 |
| J1-8外接常开键 | J13 / key_in[5] | 短按并释放：暂停滚动并向左移16像素；长按0.5秒：向左自动滚动 |
| J1-9外接常开键 | K12 / key_in[6] | 短按并释放：暂停滚动并向右移16像素；长按0.5秒：向右自动滚动 |
| 两个移动键同时按 | J13＋K12 | 暂停、恢复字幕起点 |
| SW3 | C6 | 沿用音频开启/关闭；重新开启从WAV开头播放 |
| SW4 | C5 | 沿用系统复位 |

外接键另一端接J1-12或J1-30 GND，内部上拉，按下有效。自动滚动每两帧移动1像素，约30像素/秒，文字之间保留4字符间隔。字幕关闭时冻结位置，新图片被采用后回到起点。短按在释放时判定，长按不再补发一次短按。

音量保留队友的20档0..19，KEY1减、KEY2加。J1-6源静音、J1-7 HDMI侧静音均保留；任一路静音不停止音频进度。图片切换和轮播不清零音频时间。

## 播放时间如何保证正确

WAV解码器为每次循环的首个PCM采样标记`sample_first`。该标记与样本一起经过33位PCM缓冲，再与`{enabled, real_sample, first}`标签一起进入35位音频CDC缓冲。HDMI消费一帧有效立体声PCM时才推进进度；48,000帧恰好推进1秒。

- 静音仍消费真实曲目采样，所以计数继续。
- 启动预填或欠载补出的静音不推进曲目进度；欠载时隐藏时间，恢复有效采样后继续。
- 循环首采样真正被HDMI消费时归零，不随SD读指针提前归零。无需另传易丢失的循环脉冲或曲目总长度。
- 停播标签通过同一队列到达HDMI侧时清零/隐藏；重新开启后遇到新首采样重新开始，队列中旧采样不会计入新循环。
- 时间只在视频帧边界整体更新，避免数字进位撕裂；它不是北京时间，不需要RTC或电池。时/分/秒以BCD计数，100小时回绕。

这里的“HDMI消费”指发送端从PCM队列取样，显示器自身的音视频缓存延迟不计入。

## 图片信息为什么不会提前切换

序号和短文件名附在既有帧描述上。利用frame_buffer_ctrl禁止在写入/等待提交时接收下一帧的约束，用户元数据保持在已有CDC载荷寄存器中，直到提交前台时捕获；删除了208位重复寄存器，未改SDRAM读写算法。

只有reader在垂直消隐后实际采用新前台槽位时，memory才通过请求/确认邮箱送出序号、文件名和尺寸。Display串行转换十进制信息，下一帧开始前统一切换。加载失败、取消或后台写入未完成时保留原字幕。六图轮播及槽位复用已检查；没有仅凭writer_done直接改标题。

## 为装入器件和通过时序所做的配套修改

1. 小字库：采用ZLabs 16px字体的104字形子集，源码内初始化，不依赖旧D盘字库路径；包含95个ASCII和9个中文，另有方框占位。源字体和OFL版权保留，字库生成工具使用标准库解析固定提交的KBITX数据。
2. 频谱16路log柱高换算改为复用一套电路、用16个时钟完成，并一次性发布112位结果。FFT、频段和柱高数值不变，额外延迟约0.64微秒。原FFT/频谱黄金向量和面板测试通过。
3. 20档音量百分比改为精确查表，保留`floor(level*100/19)`；百分比控制值寄存一拍，解除组合除法/绘字长路径。图像RGB、坐标和同步信号不增加像素延迟。
4. 保留既有SDRAM PLL、厂商IP、写控制器、刷新、地址算法及GPIO接线。只为新增稳定载荷/邮箱增加精确跨域约束，不放宽主时钟周期。
5. 旧osd_overlay的第二槽容量和末字符预取边界一并修正；主工程使用新的subtitle_overlay，旧GB2312大字库不实例化。
