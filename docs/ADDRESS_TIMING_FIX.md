# SDRAM 写地址长路径修复

更新：2026-10-28。用户授权检查 `-6.566 ns` 写地址建立时间违例的原因、运行影响并修复。

## 原因和实际风险

原 `sdram_write_ctrl` 直接使用组合表达式：

`base + (top_down ? y : height - 1 - y) * width + x`

倒序行号的减法、乘法及地址加法串联。无位宽限定的常量 `1` 还会将相关中间表达式扩展到 32 位。TD 原综合报告的最差路径从 `dst_height` 寄存器出发，经过 9 级逻辑（6 级加法器、2 级 LUT 和 1 级 MULT18）到厂商 IP 的 `app_wr_addr_1d`：数据路径约 14.450 ns，125 MHz 周期为 8 ns，扣除建立时间后要求 7.884 ns，因此 slack 为 -6.566 ns。

如果在有效写入采样时地址仍未稳定，可能把数据写到错误位置，产生花屏或数据破坏。报告不表示每拍必错：高度描述只在换帧时变化，部分长路径可能在当前协议的空闲期间稳定。要把这些路径按多周期处理，必须证明源变化与地址有效采样之间的关系，不能仅凭 RTL 仿真通过或“中间有空闲”就豁免。

普通 RTL 仿真没有综合、布线后的门延迟，因而不能证明这个 8 ns 电路预算满足。本次直接缩短实际有效写地址路径，不依赖隐含的空闲时间，也没有降低时钟或增加时序例外。

## 修改方法

只修改 `rtl/memory/sdram_write_ctrl.v` 的地址生成及地址就绪门控，端口和四字数据协议保持。

1. 接到描述时，锁存首行编号、宽度、最后一列，以及正/负行步长。倒序首行编号使用明确的 16 位减法。
2. 下一拍计算首行偏移 `first_row * width`，寄存为 21 位字偏移。
3. 再下一拍把基址与偏移相加，写入 `row_base_addr` 和 `current_addr`，置 `address_ready`。
4. 正常写入每拍使用寄存器 `current_addr` 输出地址；普通像素只做 `+1`，行尾只做一次 `row_base_addr + row_step`。倒序图的步长是 `-width`。
5. `write_request` 和从 PREFETCH 进入 WRITE 均等待 `address_ready`。初始化期间允许 FIFO 正常预取，地址尚未准备好时不会提交写请求。数据、使能和地址仍在同一拍对应。

初始化只在每帧描述后进行两拍，连续四字写入不增加地址流水延迟。原行列计数、完成保持/排空、刷新协调及外部复位协议保留；复位和后台取消会清除新增地址状态。

本次没有修改 PLL、ADC、SDC、厂商加密 IP、读控制器、FIFO、帧缓存管理或系统接口。用户原有注释和已删除 demo 状态保留。

### 写地址相关路径

导出全部物理终点的 Routed 报告，共检查 13238 条最大/最小时序记录，按 writer 及厂商写地址缓存终点归类，而非只看全局最差路径。

| 范围 | 建立时间最差裕量 | 保持时间最差裕量 |
| --- | --- | --- |
| 保留名称的下游写地址缓存终点 | +6.656 ns | +0.223 ns |
| writer 内部终点 | +0.019 ns | +0.076 ns |

写地址缓存有 14 个保留名称的物理终点，writer 内部有 217 个；物理打包/合并后的终点数量不等于 RTL 的总线位数。功能回归比较的是完整 21 位地址。以上路径在当前约束和角落下未见负裕量；writer 控制最小余量仅 0.019 ns，不能在没有抖动/时钟不确定性预算的情况下扩大为完整裕量保证。

原先 -6.566 ns 来自**综合估计**，新 +6.656 ns 来自**布线后分析**，两者分析阶段不同，不能相减当作同条件下的精确性能提升。结论是原长组合链已经移除，最终有效写地址路径为正裕量。

### 整个工程仍未时序收敛

**整体 Routed 最差建立裕量仍为 -6.565 ns，保持裕量 +0.030 ns。** 这个数值与旧 -6.566 ns 接近，但现在最差路径是封装 SDRAM 的 DQ 输入到 FPGA PAD，与原来的高度描述 → 写地址乘加路径不同。

剩余还包含显示 FIFO 水位到 reader 状态约 -0.384 ns，以及异步复位同步器输入的 recovery 报告等。它们分别需要检查物理接口参数/采样窗口、控制路径深度和复位时序例外的合法范围。本次不把这些独立问题标为已解决，也不凭写地址修复宣称整机可稳定上板。

SDRAM 180° 的参考模型第四字 Z、外部 SPI/HDMI 时序预算、PLL 抖动预算及最终板级验收仍单独保留。后续先处理这些剩余时序项，再进行下载验证。
