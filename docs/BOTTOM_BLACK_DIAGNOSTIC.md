# 底部黑白测试区缺失诊断（2026-10-29）

用户实板现象：图像上部色条、灰阶与 RGB 带可见，底部黑白测试区仅显示少量行，余下为黑色；用户确认 LED4 亮，目前缺失都发生在底部。未获得首次错误位置或独立错误信号的实板采样。

## 已确认

- 原图为 FFF 根目录 `test_pattern_640x480_24bit.bmp`，921654 字节，BMP 声明大小与实际一致，640×480、24 位 BI_RGB、正高度480、像素偏移54。
- 底部第376～479行包含图案，每行均有非黑像素；第479行有447个非黑像素。原图本身未缺失底部。
- 使用当前 `bmp_stream_decoder.v` 对该原图加入背压逐像素验证，307200个RGB、坐标与地址全部一致，第479行640个像素均输出。`ACTUAL_BMP_DECODE_PASS`。这验证了解码器受控输入路径，不代替实际SD卡/SPI信号验证。
- 重新运行已有 memory/display 应用模型测试通过，包含受控欠载和读响应超时后的屏蔽与恢复。测试人为注入错误用于确认行为，不证明实板一定由同一底层原因触发。
- LED4 是加载错误或显示错误的锁存汇总，按外部复位才清除；仅凭它亮，不能区分当前欠载、读超时或早先错误。

## 为什么一次错误能使后面整片变黑

`display_pixel_fifo.v:70` 在有效区请求像素、前台帧有效而输出队列为空时置 `underflow=1`；`:58` 的 `pix_valid` 被 `!underflow` 门控。本帧即使后续又收到像素，underflow仍保持，直到帧清空复位。

`sdram_read_ctrl.v:142` 在四字组的读响应等待达到256个100MHz周期（约2.56µs）时置 `read_error`，退出本帧读取；`memory_top.v:131` 将同步后的读错误用于屏蔽像素。

`read_RAM.v` 在像素无效时输出黑色。因此，若首次欠载或读超时发生在图片下部，可产生“上面正常、下面持续黑到帧尾”的现象；它不等同于已经证明底部未写进SDRAM，也不能据此直接断言已存内容正确。

## 尚未证实的根因与下一项检查

需要在实板区分 `u_display_fifo.underflow`（像素供应/队列问题）、`u_reader.read_error`（读返回超时）与 `u_player.load_error`（加载错误），并记录首次出错时 `u_display/u_read_RAM` 的 hcnt/vcnt。进一步关联 `wr_used`、reader状态、Sdr_busy、Sdr_rd_en和refresh_pending，才能判定持续吞吐不足、短时停顿、漏响应或其他板级问题。

LED4曾亮并不能单独完成此区分，现有短仿真通过也不能反证实板故障。不要仅靠加大FIFO、移除整帧黑屏门控、改PLL或放宽SDC宣称修复；这些改动尚无实板证据支持。本轮未修改模块代码、生成新bit或提交Git。

证据：`bmp_evidence.json`、`decode_result.json`、`decode_stage_1.log`、`unit/verification_results.json`。现阶段结论是源图与受控BMP解码完整，实板错误需要分项采集；尚未确定造成LED4亮的具体信号。
